# Admit P921 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Register `P921` "main subject" as an edge type so two books that share only a subject can route to each other, which returns nothing today.

**Architecture:** One property, ADR 38's shape. A registration in `EdgeTypes`, a weighing in `RecommendationWeights`, a demonstration on a scratch graph, and an ADR. No new package, no new source, no change to the ingest pipeline.

**Tech Stack:** Java 21 (release 21, toolchain 25), Gradle Kotlin DSL, JUnit 5 + AssertJ, ArchUnit.

## Global Constraints

- **Issue #111.** Branch `111-admit-p921`. Read the issue — its measurement comment is the argument.
- **Admit `P921` alone.** Not `P136` genre, `P106` occupation, `P108` employer, `P27` country. Each was measured and rejected in ADR 38, or is unmeasured.
- **Never open `~/.segue/segue.db`.** Every demonstration runs on a copy in scratch, with `--db` pointed at it. Report the real file's mtime unchanged. It holds 973 irreplaceable personal ratings.
- Stage commits **by explicit path**. NEVER `git add -A` — an untracked `mad.vcf` must never be staged.
- `./gradlew check` green before every commit; run long commands **blocking**.
- **Never invent a QID.** Confirm by label AND description. The two this targets are confirmed: `Q80006` computer programming ("the process of designing and building an executable computer program"), `Q80993` software engineering ("academic discipline that studies systematic approaches to development").
- TDD: failing test first, run it, watch it fail for the right reason, report what it actually said.

## What the measurement established

- A subject's in-graph degree is **the number of the owner's own books naming it** — one forward edge per book; the reverse pass on a book returns zero rows. Four to nine books, **below `HUB_DEGREE` (10)**, so no route is demoted and no third hub rule is needed. The margin is small and contingent: the tenth book crosses it.
- **Expanding a subject would pull up to 500 edges in one call** (religion and accounting both hit the `ReverseClaims` cap). A subject must arrive only as a book's neighbour. The general fix is #112; this plan must simply not make it worse.
- The owner's books point at `Q80006` and `Q80993`, **not** at the thirteen subjects a person would name. Tanenbaum's Computer Networks, DDD and Introduction to Algorithms carry no `P921`; Effective Java is not in Wikidata.

### Task 1: Register `P921` and weigh it

**Files:**

**Interfaces:**
- Produces: `EdgeTypes.ABOUT` (name it whatever the codebase's convention argues for — see below), registered against `P921`, and a weighing in `RecommendationWeights.BY_CODE`.

- [ ] **Step 1: Determine the direction empirically — I may have got this wrong**

Issue #111 asserts `P921` "is stated on the work, pointing at the subject, so it is `inverted` in ADR 22's sense." **Check that rather than trusting it.** Read `EdgeType.direct` / `EdgeType.inverted` and the existing registrations:

- `P50` author is stated on the book pointing at the person, and is registered **`inverted`** — because segue wants `person -AUTHORED-> book`, the reverse of the statement.
- `P921` is stated on the book pointing at the subject. If segue wants `book -ABOUT-> subject`, that is the **same** direction Wikidata states it, which would make it **`direct`**, not `inverted`.

Work out which, from what the constructors actually do, and **say in your report which it is and why**. If it is `direct`, the issue text is wrong and should be corrected in the ADR.

Also check the inverse-property trap (ADR 36's issue-#33 amendment): if Wikidata has a property that is `P921`'s inverse and it is already registered, admitting both records one relationship twice. `P527` is marked `fallbackOnly` for exactly this reason.

- [ ] **Step 2: Write the failing tests**

In `EdgeTypesTest`, following the file's existing style: the new type is registered, carries `P921`, and has the direction Step 1 established. In `RecommendationWeightsTest`, `everyRegisteredTypeIsNamed` will already be failing — that is the build telling you a new type must be weighed.

- [ ] **Step 3: Run and watch them fail.** Record the actual messages.

- [ ] **Step 4: Register and weigh**

Register in `EdgeTypes` beside the other single-property admissions, with a javadoc in the file's voice explaining what it is for and citing #111. Then weigh it in `RecommendationWeights`.

**The weight is an argument, not a number to copy.** The existing tiers are `INFLUENCE = 1.0`, `COLLABORATION = 0.5`, `RECOGNITION = 0.2`. Aboutness is neither collaboration nor recognition:

- Two books about software engineering is much weaker evidence of a connection than two people in the same band.
- ADR 38 admitted `RECEIVED_AWARD` at `RECOGNITION` precisely because single-authored work has no collaboration to find — the same argument applies here, which suggests aboutness belongs at or below that tier.
- The measurement turned up an awkward fact to confront rather than ignore: **96% of award nodes sit below `HUB_DEGREE`**, so a shared minor award already outranks a shared subject on hub count. Weighing aboutness above recognition would fight that; weighing it below compounds it.

Decide, and record the reasoning in the constant's javadoc. `esteemDirectional` should be `NO_ESTEEM` — being about a subject is not esteem in either direction — but confirm that against `asEvidenceAbout`'s contract rather than assuming.
